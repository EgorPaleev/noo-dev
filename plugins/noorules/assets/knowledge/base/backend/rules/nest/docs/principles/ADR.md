# ADR — лог архитектурных решений

`docs/*.md` описывают **текущее** состояние конвенций — что и как сделано. ADR (Architecture Decision Record) — рядом, но про другое: **почему** сделано именно так, а не иначе, когда вариантов было несколько и выбор не очевиден из кода.

## Когда заводить запись

Когда решение:

- могло быть принято иначе (есть реальная альтернатива, которую кто-то предложит снова через полгода);
- влияет на несколько модулей или всю архитектуру, а не на один файл;
- вызовет вопрос "а почему не сделали Х" у человека (или у Claude), который придёт дорабатывать код позже.

Не заводить запись под каждую мелкую правку — только под решения, которые стоит объяснять.

## Формат

Один файл на решение: `docs/adr/NNNN-short-title.md`, нумерация сквозная, записи не редактируются задним числом (если решение пересмотрено — новая запись со ссылкой на старую, статус старой меняется на `Заменено → NNNN`).

```markdown
# NNNN. Короткое название решения

Статус: Принято | Заменено → NNNN

## Контекст

Какая задача/ограничение привели к необходимости выбора. Какие варианты рассматривались.

## Решение

Что выбрали.

## Последствия

Что это даёт и чем приходится платить (trade-off), включая то, что теперь принципиально нельзя/сложнее сделать.
```

## Важно: без ретроактивных записей "на угад"

На момент создания этого лога в репозитории уже есть решения, для которых была бы уместна ADR-запись (например: Fastify вместо Express, `cache-manager`/`@keyv/redis` вместо `ioredis` напрямую, `@stylistic/eslint-plugin` вместо Prettier, Prisma без repository-слоя). Записи под них **намеренно не созданы задним числом** — реальная причина выбора неизвестна (не задокументирована и не восстанавливается из кода), а придуманное "правдоподобное" обоснование хуже отсутствия записи: оно выглядит как факт и вводит в заблуждение.

Если реальная причина этих решений известна автору — стоит явно задать вопрос и записать. Новые решения фиксируются по мере принятия, начиная с `0001`.
