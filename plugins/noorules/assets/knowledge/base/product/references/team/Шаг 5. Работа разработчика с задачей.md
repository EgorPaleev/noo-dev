
Сквозной флоу от момента взятия задачи в работу до передачи на тестирование и закрытия через приёмку.

---

## 1. Взять задачу в работу

Стадия «Взять в работу» означает что разработчик начал знакомиться с задачей — читает ТЗ, разбирается в контексте, задаёт вопросы если нужно. Это время также фиксируется в задачу.

Когда разработчик переходит непосредственно к написанию кода — создаётся ветка.

---

## 2. Создание ветки

Перед созданием ветки обновить локальный `dev`:

```
git checkout dev
git pull origin dev
```

Создать ветку по шаблону: `feature/bitrix-task-{номер задачи}`

Одна ветка = одна задача.

---

## 3. Коммиты

Формат — императивная форма (`feat:`, `fix:`, `refactor:`, `chore:`).

```
feat: добавить экран профиля пользователя
fix: исправить краш при открытии чата
fix: поправить отступы на карточке заказа
refactor: вынести логику валидации в отдельный класс
chore: обновить версию зависимости Retrofit
```

Периодичность:
- Если задача выполняется в течение одного дня — желательно один коммит.
- Если задача большая и растягивается на несколько календарных дней — допускается несколько коммитов, по логическим частям работы.

Это позволит без труда обращаться к Git'у как к "Журналу изменений" и улучшит качество работы.

---

## 4. Актуальность ветки

Перед созданием новой ветки — актуализировать `dev` и ответвляться от него (см. шаг 2).

Каждый раз возвращаясь к работе над веткой — актуализировать её относительно `dev`:

```
git fetch origin
git rebase origin/dev
```

Конфликты решаются локально. Если МР требуют решения — тегнуть в чате задачи/ТГ разработчика, чья ветка конфликтует, и приложить ссылку на задачу.

---

## 5. Создание Merge Request

После завершения реализации — создать MR через интерфейс GitLab:

- **Откуда:** `feature/bitrix-task-{номер}`
- **Куда:** `dev`
- **Название:** совпадает с названием задачи в Битрикс
- **Описание:** кратко что сделано, нюансы если есть
- Проставить ревьюера 

Ссылка на MR кладётся в чат задачи в Битрикс.

---

## 6. Если возникает блокер

Если в процессе работы разработчик упёрся в блокер (например ждёт ответ от бэка, недоступен стенд) — это сообщается в чат задачи. Если блокер влияет на срок — это также повод сообщить о сдвиге сроков заранее (см. «Жизненный цикл задачи», п.4 «В работе»).

---

## 7. Жизненный цикл MR

MR держится открытым с момента передачи на тестирование до перехода задачи на стадию «Приёмка».

Если на тестировании найдены баги и задача возвращается на «На доработке» — разработчик возвращается в **ту же ветку**, делает фикс-коммиты в императивной форме (например `fix: ...`), актуализирует ветку относительно `dev` и пушит — без создания новой ветки или нового MR.

MR мержится в `dev` только когда задача успешно прошла приёмку без замечаний.

После мержа ветку `feature/...` можно удалить локально. На GitLab ветку сразу удалять не нужно.

---

## 8. Передача на тестирование

При переводе задачи на стадию «Готово к тестированию» разработчик отдельно указывает:

- ссылка на MR
- краткий комментарий — опционально
- ссылка на диск с результатом (например APK) — опционально

---

## Пример на практике

**Задача:** «Добавить на главную страницу пагинацию» (bitrix-task-12345)

1. **Взять в работу** — разработчик читает ТЗ, уточняет у менеджера сколько элементов на страницу (по умолчанию — 20). Переходит к коду.

2. **Создание ветки:**
```
git checkout dev
git pull origin dev
git checkout -b feature/bitrix-task-12345
```

3. **Реализация и коммит** (задача в рамках одного дня → один коммит):
```
feat: добавить пагинацию на главную страницу
```

4. **Создание MR** — `feature/bitrix-task-12345` → `dev`, название «Добавить на главную страницу пагинацию», в описании — «Реализована пагинация по 20 элементов, подгрузка при скролле». Проставлен ревьюер. Ссылка на MR → в чат задачи.

5. **Передача на тестирование** — в чат задачи: ссылка на MR + комментарий «Реализована пагинация по 20 элементов на страницу». Задача переводится в «Готово к тестированию».

6. **Возврат с тестирования** — QA находит дублирование элементов при быстром скролле, задача переходит в «На доработке». Разработчик возвращается в ту же ветку `feature/bitrix-task-12345`:
```
git fetch origin
git rebase origin/dev
```
Исправляет баг, коммитит:
```
fix: устранить дублирование элементов при быстром скролле
```
Пушит в тот же MR. Переводит задачу обратно в «Готово к тестированию» → «Тестирование».

7. **После приёмки** — задача прошла приёмку без замечаний. MR мержится в `dev`. Ветка `feature/bitrix-task-12345` удаляется локально (на GitLab — остаётся).
