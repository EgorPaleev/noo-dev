# 0007. Сокет чатов на уровне саммита

## Status

Proposed

## Context

Бэкенд отдаёт один WebSocket на саммит: `GET /api/summits/{summitID}/chats/ws`. По нему приходят:

- `message.created` — входящее сообщение (только адресату, в кадре только `message`);
- `message.sent` — подтверждение своего сообщения (с полным `chat`, включая `unread_count`);
- `message.read` — собеседник прочитал наши сообщения;
- `news.created` / `news.updated` — новости саммита (всем участникам);
- `error` — бизнес-ошибки отправки.

Рассылка ephemeral: после каждого переподключения клиент сверяет состояние по REST.

Раньше сокет открывал только экран диалога (`ChatRepositoryImpl.observeConversation`), а закрывал
`ChatViewModel.onCleared()`. Вне диалога события не приходили, поэтому на главном экране не было
отметки непрочитанного (QA #26), а список чатов обновлялся только при открытии. Кроме того, второй
подписчик `ChatSocket.connect()` закрывал сессию первого, а `close()` из чужого `onCleared` гасил
активное соединение.

## Decision

- **Одно соединение на саммит.** `SummitSocketSession` (`:core:data`, Koin `single`) — единственный
  подписчик `ChatSocket.connect(summitId)`. `start()` читает текущий саммит и подключается (при
  смене саммита переподключается), `stop()` отменяет подписку. Команды обрабатываются по очереди.
- **Кто запускает.** `App.kt`: `LifecycleStartEffect`, пока в back stack есть `MainScreen` (корень
  любого стека внутри саммита) или `Chat` (диалог из пуша). На `ON_STOP` (свернули приложение)
  сокет закрывается, на `ON_START` открывается снова. Это покрывает вход в саммит, перезапуск
  через Splash и восстановление стека после смерти процесса. `LeaveSummitRepository` и
  `LogoutRepository` дополнительно вызывают `stop()` до очистки кэшей.
- **Кто обрабатывает.** Фичи регистрируют `SummitSocketHandler` через Koin
  (`bind<SummitSocketHandler>()`), сессия получает их через `getAll()`. Так `:core:data` не
  зависит от фич, и каждая фича пишет только в свою таблицу:
  - `ChatSocketEventHandler` (`feature-chat-impl`) — сообщения в `chat_messages_cache`;
  - `ChatsListSocketHandler` (`feature-chats-list-impl`) — непрочитанное и последнее сообщение
    в `summit_chats_cache`;
  - `NewsSocketHandler` (`feature-news-impl`) — `summit_news_cache`.

  Обработчики вызываются последовательно; исключение одного логируется и не рвёт поток.
- **Непрочитанное.** `GET /chats/with/{id}` не отдаёт `unread_count`, поэтому счётчик ведётся
  локально и сверяется с сервером:
  - на каждый переход сокета в `Connected` — перезагрузка первой страницы `GET /chats` и `GET /news`;
  - `message.created` — `unreadCount + 1` и последнее сообщение (повтор того же сообщения не
    считается); неизвестный чат — перезагрузка первой страницы;
  - `message.sent` — upsert чата из кадра с сохранением имени и аватара;
  - своё прочтение (`PUT .../read` прошёл) — счётчик = число входящих после отметки.
- **Отметка на главном экране.** `ObserveChatsBadgeUseCase` (`feature-chats-list-api`) =
  есть чат с `unreadCount > 0` **или** непрочитанная новость (как в макете case-5-home).
  `ScreenSection.hasBadge` у плитки «Чаты».
- **Диалог** больше не открывает и не закрывает сокет: он читает Room и `connectState`
  (сверка истории и дослать неотправленное — при открытии и на каждом переходе в `Connected`).

## Consequences

- Отметка на главном экране и точки в списке чатов обновляются вживую, без перезахода на экран.
- Пока приложение в фоне, сокета нет; о новых сообщениях сообщают пуши, а состояние
  сверяется при возврате.
- Прочтение на другом устройстве событием не приходит: отметка погаснет при следующем
  подключении или открытии списка.
- Непрочитанные чаты дальше первой страницы (30) не учитываются.
- Ping у WebSocket не настроен: «мёртвое» соединение после смены сети может обнаружиться не сразу.
- Новая фича, которой нужны события сокета, добавляет свой `SummitSocketHandler`, не открывая
  второе соединение.
