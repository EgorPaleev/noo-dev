# Состояние запуска

Храни служебное состояние в `.noorules/runs/<id>/run.json`. ID состоит из строчных латинских букв, цифр и дефисов. Одному запуску соответствует один активный исполнитель. Перед обновлением перечитывай состояние и проверяй, что этап ещё не завершён в другом сеансе.

## Где сохранять файлы

- Перед записью проверь локальное исключение командой `sh <путь-к-noo-flow>/scripts/prepare-run-storage.sh <id>` из рабочей копии. Скрипт добавляет `/.noorules/runs/` в локальный Git-файл `info/exclude` при необходимости и подтверждает исключение. Создавай служебные файлы после успешной проверки исключения. Если исключение недоступно, продолжи в текущем чате. Учитывай в нём статусы и результаты этапов, передавай их следующим этапам и сообщи об ограничении восстановления по ID.
- Сохраняй согласованный план в `.noorules/runs/<id>/work/plan.md`, а одноразовые результаты этапов и файлы субагентов в отдельных файлах внутри `work/`. Этот каталог предназначен для временных файлов. Для кода и отчётов, которые потребуются после закрытия, используй канонические или явно указанные пути вне временного каталога.
- Выбери разные пути для независимых этапов. Сохраняй существующие файлы, если пользователь не поручил их обновить. При продолжении старого запуска читай прежние пути из `run.json`, а новые служебные результаты сохраняй в каталоге запуска. Если старый `run.json` отслеживается Git, оставь его источником для чтения и создай локальную запись продолжения под новым ID.
- Записывай в `run.json` относительные ссылки на план, результаты и файлы, от которых они зависят. Перед созданием записи нового согласованного запуска выполни очистку по правилам ниже.

## Прогресс

- При старте этапа запиши `running` и сообщи в чате его номер, название, текущую работу и следующий шаг. Например, «2 из 4 · Реализация. Пишу код очистки. Дальше запущу проверки».
- Внутри этапа сообщай о значимых переходах, например к написанию кода, прогону тестов, исправлению замечаний, проверке индекса или подготовке отправки. Для фактически запущенного субагента назови его задачу и что выполняется параллельно. После возврата кратко сообщи результат и что пойдёт дальше. Сообщай о существенных задержках и блокерах. Обновления не требуют ответа.
- Храни последнюю текущую работу в `activity` этапа. Укажи `message`, `executor` со значением `chat` или `subagent` и время `updatedAt` в UTC. При завершении или блокере отметь статус. По запросу статуса покажи ID, завершённые и ожидающие этапы, текущую работу и исполнителей, ближайший готовый шаг и известный блокер. После прерывания сеанса трактуй `running` как последнюю сохранённую отметку. Перед повтором проверь рабочую ветку и наличие результата, чтобы принять уже сделанную работу.

## Завершение и очистка

- Подготовь итог для чата и сохрани явно запрошенные материалы по их назначению. Когда все согласованные этапы завершены, добавь `"closed": true` в `run.json`. Запиши обновлённое состояние во временный файл рядом и переименуй его в `run.json`. Вопрос, куда отправить готовый локальный результат, можно задать вместе с итогом и именем ветки. Если публикация уже входит в согласованные этапы и заблокирована, запуск остаётся открытым.
- При закрытии и в начале следующего согласованного запуска вызови `python3 <путь-к-noo-flow>/scripts/prune-runs.py` из рабочей копии. Скрипт удаляет временные файлы и запись закрытого запуска. Он также очищает старые архивные итоги с отметкой о закрытии. Открытые запуски, их зависимости, записи с явным сохранением материалов и файлы в Git сохраняются. Для записей без отметки о закрытии состояние считается открытым. Если Python 3 недоступен или очистка завершилась ошибкой, продолжи работу и сообщи, что очистку пропустили.
- Для повторного использования в будущих задачах сохраняй нужный результат отдельно от временных файлов. Для уже принятого входа другого запуска сохраняй относительный путь или `sourceRun` в его состоянии, чтобы очистка учитывала эту зависимость.

При создании или ремонте записи используй [схему run.json](../../../assets/knowledge/flow-run.schema.json). Строки отпечатков ниже приведены для примера.

```json
{
  "schemaVersion": 1,
  "pipeline": "review-only",
  "pluginVersion": "0.5.0",
  "plan": {
    "path": ".noorules/runs/feature-review/work/plan.md",
    "fingerprint": "git:0123456789abcdef0123456789abcdef01234567"
  },
  "steps": [
    {
      "id": "review",
      "task": "code-review",
      "skill": "noo-review",
      "inputs": ["change-set"],
      "optionalInputs": ["verification-report"],
      "output": "review-report",
      "status": "completed",
      "usedInputs": {
        "change-set": {"path": "work/changes.diff", "fingerprint": "git:0123456789abcdef0123456789abcdef01234567"}
      },
      "result": {
        "path": ".noorules/runs/feature-review/work/review-report.md",
        "fingerprint": "git:abcdef0123456789abcdef0123456789abcdef01"
      }
    }
  ],
  "externalInputs": {
    "change-set": {"path": "work/changes.diff", "fingerprint": "git:0123456789abcdef0123456789abcdef01234567"}
  }
}
```

- После одобрения укажи путь и отпечаток файла плана в поле `plan`. Запиши этапы со статусом `pending` и их контрактами. Храни обязательные входы в `inputs`, необязательные — в `optionalInputs`. Готовый этап имеет все обязательные входы и завершённые зависимости из `dependsOn`. Для старых запусков сохраняй список `inputs` и прежний порядок готовности. Отсутствующее поле `optionalInputs` означает пустой список.
- Для запуска с этапом `working-branch` при возобновлении прочитай его сохранённый результат и проверь рабочую копию по [`noo-branch`](../../noo-branch/SKILL.md). Считай этап готовым после проверки артефакта и рабочей ветки. Пока такой контекст недоступен, зависимые этапы ждут.
- Для входа этапа используй результат предшественника, который объявляет нужный артефакт. Если несколько предшественников объявляют одинаковое имя, зафиксируй однозначный источник в плане или используй разные имена для выходов. При отсутствии этапа-источника ищи файл в `externalInputs`. Отсутствующий или изменившийся обязательный вход фиксируй как ожидание. Пропусти недоступный необязательный вход и отметь ограничение, если оно влияет на результат. Для любого фактически использованного входа сохрани отпечаток в `usedInputs`. Независимый этап можно продолжить.
- Записывай путь относительно проекта. Для отпечатка используй `git hash-object --no-filters -- <путь>` либо SHA-256. Укажи метод в поле `fingerprint`. Если автоматическая проверка недоступна, сохрани копию файла и запиши её путь в `snapshotPath`.
- После выполнения навыка запиши файл результата, использованные входы и статус `completed`. Статус без результата не закрывает этап. Уточнение, решение человека или отсутствующий вход фиксируй как `waiting` с причиной.
- В `appliedMaterials.skills` и `appliedMaterials.rules` сохраняй имена фактически применённых навыков и ID или пути правил. В `appliedMaterials.uses` укажи для каждого материала пару `material` и `effect`, которая объясняет конкретное решение или проверку.
- В `model` каждого нового этапа сохраняй `level` и `reason`, а при подтверждённой доступности модели — её ID в `recommended` и настройку `reasoningEffort`. Записывай `used` и `usedReasoningEffort` только по данным среды. Если плановый выбор нельзя применить, укажи `fallbackReason`.
- Если результат ссылается на отдельный diff или файлы результата, запиши их пути и отпечатки в `dependencies` рядом с основным артефактом. Проверяй их при повторном использовании так же, как основной файл.
- При продолжении сначала сверяй версии контрактов оставшихся шагов, затем файлы и их отпечатки. Изменившийся результат и завершённые шаги, которые зависели от него прямо или через другие результаты, помечай `stale` с причиной. Для необязательного артефакта учитывай зависимость завершённого шага, если артефакт записан в `usedInputs`. Неисполненный шаг без обязательного входа получает `waiting`. Независимые этапы сохраняют свои результаты. Прежние файлы сохраняй, обновлённую часть запускай под отдельным ID или используй согласованную версию входа.
- При сравнении сохранённого контракта с текущим считай имена `noorules-<имя>` и `noo-<имя>` одним навыком, если короткое имя совпадает с назначением в действующем сценарии. Для следующего шага открывай навык по текущему имени. Смена префикса сама по себе сохраняет статус и артефакты.
