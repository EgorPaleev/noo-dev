# Подбор и сборка пайплайна

1. Начни с запрошенных результатов, файлов и ID. Используй [контекст, собранный при планировании](../../noo-rules/references/project-context.md#контекст-между-этапами), и дочитай материалы, необходимые для выбора. Сначала используй ближайшие совпадения по путям, названиям или ID. Открывай историю или карту маршрутов, когда этих данных недостаточно.
2. Если пользователь назвал пайплайн или его требует проект, возьми это определение за основу плана. Для явно названного маршрута используй его контракт. Если задача подходит под [короткий маршрут](#короткий-маршрут), предложи его сразу. В остальных случаях сначала проверь совпавший проектный пайплайн, затем [встроенные сценарии](../../../assets/knowledge/flows.json). Выбирай сценарий по нужным результатам. Если совпадения нет, собери цепочку из [подходящих маршрутов](../../../assets/knowledge/task-index.md). Для этапа без маршрута задай ID, цель, входы, результат и проверку, затем выбери навык или исполнение в текущем чате.
3. Для каждого запрошенного результата определи этап, обязательные и необязательные входы, зависимости и проверку. Если подходящий артефакт уже есть, используй его вместо повторного этапа. Сопоставляй входы по содержанию. Например, описание поведения и журнал ошибок могут дать вводные для диагностики без отдельного ТЗ. Если пользователь просит обновить артефакт, бери его за основу изменения. Добавляй промежуточный этап, если без него нет обязательного входа или проверки. Используй доступный необязательный вход, если он относится к задаче. Его отсутствие само по себе не добавляет этап. Для ревью достаточно diff, для спецификации — согласованного кейса. Связанные этапы с общим анализом объединяй, когда разделение дублирует работу. Независимые ветки отмечай для параллельного запуска.
4. Для каждого этапа учти явно запрошенный навык и подходящие навыки проекта, клиента и плагина. Проверь их по входам и ожидаемому результату. Покажи, какие навыки и правила нужны, какие файлы уже готовы, что надо добавить и что зависит от чего. Если запрос был только на рекомендацию, остановись после предложения. Если нужно выполнить работу, перейди к [согласованию](approval.md).

## Первый этап разработки

Если новый запуск предполагает правки файлов проекта, добавь первым этап `prepare-branch` с маршрутом `working-branch`, навыком [`noo-branch`](../../noo-branch/SKILL.md) и результатом `working-branch`. Это правило действует для встроенного, проектного и собранного под задачу пайплайна. Если такой этап уже есть, используй его один раз. Назначь его координатору. Добавь его ID в `dependsOn` остальных этапов с сохранением их зависимостей. В плане укажи имя ветки по правилам `noo-branch`, выбранную базу или правило её определения и проверку, что текущая ветка создана от полученного коммита. Для запуска, который ограничен чтением проекта и отчётом, например `review-only`, оставь текущую рабочую копию.

## Короткий маршрут

Выбирай его для локальной правки с понятным ожидаемым поведением, определённой областью изменений и доступной целевой проверкой. Предложи два этапа в текущем чате: подготовка ветки, затем реализация и обязательные проверки проекта. Для результата реализации используй один короткий отчёт. Если для этой задачи обязателен отдельный этап, например независимое ревью, добавь его к плану.

Для более крупной правки добавь проверки и ревью сообразно области изменений. Этапы уточнения, QA, приёмки и подготовки выпуска включай, когда они нужны для запрошенных результатов или обязательны по правилам проекта. Полный `product-change` подходит, когда нужен весь его набор результатов или пользователь назвал его явно.

## Пайплайны проекта

По запросу «сохрани пайплайн под именем …» возьми названную или последнюю цепочку из этого диалога и сохрани её как `.noorules/pipelines/<id>.json`. Согласованная цепочка из прошлого запуска берётся из его состояния. Если под этим именем уже сохранена та же цепочка, укажи её путь. Для замены другого определения дождись разрешения. Определение можно хранить в Git и запускать в другой рабочей копии репозитория через `noo-flow`. Дай этапам устойчивые ID и объявляй входы по их роли. Статусы, отпечатки, фактические пути и данные клиента относятся к конкретному запуску.

```json
{
  "title": "API по готовому кейсу",
  "when": "Есть согласованный функциональный кейс, нужна реализация HTTP API и её проверка",
  "steps": [
    {
      "id": "api",
      "task": "api-endpoint",
      "inputs": ["functional-case"],
      "output": "change-set"
    },
    {
      "id": "verify",
      "task": "test",
      "inputs": ["functional-case", "change-set"],
      "dependsOn": ["api"],
      "output": "verification-report"
    }
  ]
}
```

В `steps` используй поля `id`, `task`, `inputs`, `output` и при необходимости `optionalInputs`, `skill`, `dependsOn` и `goal`. Для этапа со своим ID задачи укажи `goal`. В `inputs` перечисли обязательные входы, в `optionalInputs` — необязательные. Один вход может появиться только в одном списке. Если выбранный пайплайн включает этап, которого нужно дождаться ради необязательного по маршруту результата, задай его ID явно в `dependsOn`. Например, в полном сценарии ревью ждёт предусмотренный этап проверок, а отдельное ревью берёт отчёт, только если он уже есть. Если `skill` не указан, подбери его по контракту этапа. Для навыка проекта сохрани ID в `skill`, а путь к `SKILL.md` укажи в плане. Перед запуском проверь доступность указанных навыков, источники обязательных входов и зависимости. Проверь, что в графе нет циклов. Для автоматической рекомендации ищи подходящее определение по имени, `title` или `when`.

## Повторное использование результатов

- Используй существующий кейс, решение, компонент, тест, демо или отчёт как вход, если он покрывает нужный шаг. Ссылайся на исходный файл. Если есть только часть результата, добавь недостающее к тому же материалу, когда это входит в согласованный план.
- Для результата прошлого запуска проверь статус, отпечатки файла и важных входов, затем сверяй объём с новым запросом. Изменившийся или предварительный результат используй как вводные с указанием ограничения либо проверь заново ту часть, которая нужна. Для принятого входа запиши путь и отпечаток в `externalInputs`. Источник из прошлого запуска можно указать в `sourceRun`.
- Когда результат предназначен для дальнейшей работы команды, укажи в плане его канонический путь и способ проверки. Используй существующее место для кода, тестов, демо и документации. Одноразовые результаты сохраняй [локально рядом с состоянием запуска](state.md#где-сохранять-файлы) или по пути, который указал пользователь. В итоговом ответе укажи точку входа, способ запуска или проверки и применимые ограничения.
